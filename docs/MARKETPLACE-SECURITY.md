# Marketplace security and limits

Tested boundaries: expiring hashed bearer principals; MCP session credential binding; provider/buyer tenant checks; administrator-only status/settlement operations; a local-only human purchase approval bound to buyer, capability, input hash, idempotency key, quote hash and expiry; strict tool schemas; bounded JSON; registration rate limits; shared payment-file locking and nonce reservation; private artifact root confinement; HTTPS/DNS-pinned provider transport, redirect rejection, deadline and response-size limits; output schema validation; private contact/path omission.

The human approval file is created through the local operator command, never an MCP tool. An LLM-supplied approval boolean is not accepted. SDK tool execution metadata reports taskSupport=forbidden. A signed authorization is still validated by the existing x402 canonicalization, policy and facilitator functions. The same receiver and mainnet gate apply. No private key or provider payout implementation exists.

Marketplace stores request/payment hashes, not raw signatures. It writes a purchase journal and reserves the shared nonce before contacting the facilitator. Payment failures and uncertain settlements remain visible. A process crash with an unfinished purchase is not retried automatically. Operator reconciliation is required; a stale exclusive lock must be investigated and recovered manually, never time-expired blindly. Existing x402 requests now share the file lock to prevent cross-path concurrent settlement.

Paid delivery failure retains a receipt, suspended entitlement and disputed allocation. Balances are payable only after validated delivery. This is accounting protection, not an automatic refund guarantee. External settlement response uncertainty must be reconciled against authoritative payment evidence. Persistence uses durable atomic replacement; filesystem failure during a monetary transaction still requires reconciliation. Do not run multiple hosts against the JSON files.

Abuse limits: 120 calls/minute per marketplace principal or anonymous direct peer; 10 registration/intake writes/minute; at most 2000 rate buckets; 10000 records per intake/provider/capability/purchase collection; 64 MiB serialized store cap; paginated catalog/allocation outputs. Reverse-proxy forwarded IPs are not trusted by default, so anonymous callers behind one proxy share a quota. Availability is limited by a global payment lock; busy requests fail before payment and can be retried with the same key.

Private provider URLs, credentials and arbitrary local paths are forbidden in manifests. Operator bindings are privileged configuration. DNS records are checked for private, link-local, multicast, documentation and transition ranges; the selected public address is pinned into the HTTPS connection. TLS uses normal hostname/certificate validation; redirects are refused. Custom local adapters must be bounded/cooperative with cancellation; this build ships no general local shell/module executor.

Limits: general JSON Schema is intentionally unsupported. HTTP/MCP adapters have controlled transport tests; the MCP adapter also passed a real HTTPS initialize/call/close cycle against CrossingKey's existing public payment.methods free tool (three methods, agent_spend=false). Contracted third-party providers and real paid external fulfillment have not been tested. Digital artifact files must be operator-controlled and immutable during delivery. Bearer credential provisioning/rotation uses an existing secure operator channel, not an OAuth onboarding UI. This version does not claim third-party audit, legal compliance, live settlement proof or automatic financial recovery.

Secret scan command: node scripts/scan-marketplace-secrets.mjs --staged. It reports filenames/categories only. Also run npm audit --omit=dev. Pattern scanning and a clean vulnerability database result have defined scope; they do not prove absence of every secret or vulnerability.
